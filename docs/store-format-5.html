Specification

FlatSQL store format 5

Each feed is one linear stream of size-prefixed FlatBuffers. Sibling metadata, checkpoint and segment frames make the stream the only authority: every index is a cache rebuilt from it, every record is a raw-leaf IPFS block pinned where it lies, and a backup is a CARv2 of the feed's root.

[u32 LE size][FlatBuffer] $FMB · $FCK · $FSG CIDv1 raw · sha2-256 CARv2 backups SDS 1.255.0

#Scope

This page specifies store format 5 of FlatSQL's partition store: a feed's bytes on disk, what an acknowledgment promises, how a feed is rebuilt from its own stream, and how a feed maps to IPLD (per-record CIDs, the feed root DAG and CARv2 backups). The node's side of IPFS (filestore registration, providing and pin policy) is summarized in §11.

#0Principles

  1. The stream is the only authority. Each feed is one linear stream of [u32 LE size][FlatBuffer] frames, appended in order. Everything needed to rebuild the feed is in those frames: the records, their metadata and the checkpointed state. Everything else is a cache derived from the stream: the SQLite index, the type index, the views, the IPLD link nodes and the CARs. Any of it can be deleted and rebuilt.
  2. Records are verbatim. A record frame holds exactly the bytes that arrived. No envelope, header or trailer is ever put around a record. Metadata goes in sibling frames.
  3. One record is one contiguous byte range. The raw-leaf CIDv1 (sha2-256) of that range is the record's IPFS block. Ranges are never changed while a filestore entry can name them.
  4. Every frame is a standard FlatBuffer. Each frame is identified by its 4-byte file identifier. The non-record frames are SDS tables (§3). A stock FlatBuffers reader walks the file from byte 0 and dispatches on the identifier. It needs no FlatSQL code.
  5. One format. A store in an earlier format is refused with P4_E_FORMAT, and a node rebuilds it by re-syncing its feeds.
  6. Each value lives in exactly one place. A value that can be re-derived from the record bytes is not stored again: the epoch and the object key are re-extracted on rebuild. $FMB holds only what the bytes cannot give. Checkpoint segments are derived snapshots that can be discarded; the authoritative data is the records plus their $FMB frames.

#1Files

<data>/fsql4/
  STORE                    64 B, magic FSQ4, format 5 (any other format: P4_E_FORMAT)
  T/<TYPE>.spec            registered spec TLV
  T/<TYPE>.idx             type index: CACHE (feed and token registries, rebuilt from the streams)
  T/<TYPE>.fts             full text: CACHE
  P/<TYPE>/<feed>[.<gen>].fsdata   THE FEED: the linear frame stream (§2)
  P/<TYPE>/<feed>.db       SQLite index: CACHE (optional per workload, §7)
  • Only the .fsdata stream is durable state. The SQLite index, the type index and the full-text index are caches.
  • A feed's instances, token counts, ingest identities, moves and counters are derived state, folded from the stream.
  • A feed has one stream file per generation. Compaction writes generation g+1 and retires g (§10).

#2The stream

#2.1Frame bytes

frame at offset F:
  F+0  u32 LE  N            size of the FlatBuffer; no flag bits, N >= 8
  F+4  N bytes FlatBuffer   [u32 root uoffset][4-byte file identifier][...]
next frame at F + 4 + N; the file ends exactly at a frame end.
  • There is no file header, magic, padding, CRC or trailer.
  • A frame's offset is F, the offset of its size prefix.
  • Its range is [F+4, F+4+N), the FlatBuffer bytes only.
  • The identifier at F+8..F+12 (bytes 4..8 of the FlatBuffer) names the kind:
KindIdentifierWritten whenHolds
recordthe type's ($OMM, $WXF, ...) or a sealed envelopea new record or new bytes enter the feedthe record bytes exactly as they arrived
metadata$FMBonce per feed per commit round, after that round's record frames; also alone for removalsthe round's rows, dictionary additions and removals (§3.1)
checkpoint$FCKat stream creation (genesis), then on the cadence in §6the feed's identity, counters and live segment list (§3.2)
segment$FSGat checkpoints and in LSM mergesan immutable sorted state segment (§3.3)
  • Reserved identifiers. A type cannot be registered with the identifier FMB, FCK or FSG. A record of another type is refused if it carries one of them (P4_REJ_FID), so no record frame can pose as a metadata frame.
  • The commit chain. Every non-record frame carries SELF_OFFSET (its own F) and PREVIOUS (the F of the non-record frame before it). Genesis has PREVIOUS = 2^64-1. Recovery walks this chain (§9). It never classifies a frame by its identifier alone.
  • Alignment. Frames are back to back, so a FlatBuffer may start at 4 mod 8.
    • Record frames are read in place.
    • Metadata, checkpoint and segment frames are read only at open, recovery, rebuild and DAG or CAR export. They are copied into an 8-aligned buffer before verification. No padding frames are written.

#2.2Record frames

  • Bytes. N bytes, verbatim. A sealed record's frame is its sealed envelope (SDF1/SDFN).
  • The record CID. The record CID is SDN's key and the stored CID. For an unsealed record it is CIDv1(raw 0x55, sha2-256(range)): text bafkrei..., binary 01 55 12 20 || digest.
    • The ingest check kVerifyCid (on by default) computes this digest and refuses a mismatch (P4_REJ_CID). So the stored CID is the range's raw-leaf CID, with no extra hashing.
    • A type configured without kVerifyCid has the digest computed at write. A store never holds a record CID that differs from its range, except for sealed records.
  • Sealed records. The record CID is the plaintext's (SDN's key). The leaf CID is the ciphertext range's sha2-256. The metadata frame carries both (§3.1), and IPFS sees only the leaf CID. Encrypted feeds are addressed by ciphertext.
  • Records over 1 MiB (N > 1,048,576) become a UnixFS file DAG (§4.2). The record CID stays the raw sha2-256 of the whole range (SDN's key). IPFS sees the DAG root and its 1 MiB raw leaves.
  • Shared frames. A record's copies and instances share one frame when the bytes are equal. A row that points at an earlier frame adds no record frame.

#2.3What a stock reader sees

  • A loop from byte 0 reads N, slices [F+4, F+4+N), reads the identifier and verifies with that root type.
  • The SDS readers for $FMB, $FCK and $FSG (§3) decode the metadata.
  • To list a feed's live records with no FlatSQL code, follow the newest checkpoint's segments, or replay the metadata frames (§9).

#3Metadata, checkpoint and segment tables

The three non-record kinds are SDS standards in the FlatSQL family, beside FSB and FSO: FMB (batch metadata), FCK (checkpoint) and FSG (segment), released in SDS 1.255.0. The schemas below are those standards. No earlier SDS table fits these roles:

  • FSB is opaque by contract: a reader must not interpret its data.
  • PNM announces a single object.
  • DPM is a signed publication manifest, with no per-record offset, sequence or dictionary.
  • REC wraps a record, which principle 2 forbids.

Conventions:

  • Fixed-width per-row data is in structs (zero-copy vectors).
  • Digests are [ubyte] vectors with a 32-byte stride, parallel to the struct vector. Fixed arrays in structs are avoided because some SDS languages lack them.
  • Ids are feed-scoped, except TOKEN ids, which are type-scoped.
  • 0 means "none" for every *_ID. EPOCH = INT64_MIN means no epoch.
  • Offsets are u64 and local to the stream. They are never trusted across copies (§8).

#3.1$FMB: batch metadata (one per feed per commit round)

FlatBuffers schema
// FMB: FlatSQL batch metadata. Sibling of the record frames it commits; never holds record bytes.
enum fmbDictKind : ubyte { TOKEN, NODE, BATCH, CONTENT_KEY, URL, OBJECT_KEY }
enum fmbRemoveReason : ubyte { DELETE, SUPERSEDE, CAT_SUPERSEDE, QUOTA, RETENTION, MOVED_OUT }

/// One row = one delivery of one record to this feed (rid = SEQ << 16 | ROW_J). 40 bytes.
/// No epoch or object key: both are re-extracted from the record bytes (principle 6).
struct FMBRow {
  OFFSET:ulong;          // F of the record frame (this round's, or an earlier shared frame)
  SEQ:ulong;             // the record's seq in the type's seq space
  SOURCE_TS:long;        // the copy's source timestamp: a PUT field (tag 53 entry), not in the bytes
  LENGTH:uint;           // N of the record frame
  GROUP:ushort;          // index into GROUPS
  ROW_J:ushort;          // j of the rid
  FLAGS:uint;            // bit0 NEW_FRAME (frame written this round), bit1 SEALED, bit2 LARGE,
                         // bit3 MOVED_IN (local -> feed, seq kept), bit4 COMPACTED (re-emitted by a compaction),
                         // bit5 COPY, bit6 RETAG, others 0
  RESERVED:uint;         // 0
}
/// What a call's rows share. 24 bytes.
struct FMBGroup {
  DELIVERED_AT:long;     // when this feed delivered the rows
  NODE_ID:uint;          // NODE (producer, peer)
  BATCH_ID:uint;         // BATCH (batch, producer peer, producer key)
  CONTENT_KEY_ID:uint;
  URL_ID:uint;
}
struct FMBRemove { SEQ:ulong; ROW_J:uint; REASON:fmbRemoveReason; }   // ROW_J 0xFFFFFFFF: every row of SEQ
struct FMBUrl    { SEQ:ulong; ROW_J:uint; URL_ID:uint; }               // a duplicate delivery moving a row's url
table FMBEntry   { KIND:fmbDictKind; ID:uint; TEXT:[string]; }         // TOKEN [token, peer]; NODE [producer, peer];
                                                                       // BATCH [batch, ppeer, pkey]; others [value]
table FMBSignature { ROW:uint; BYTES:[ubyte]; }                        // the row's signature
table FMBSealed  { ROW:uint; EPOCH:long = -9223372036854775808;        // ciphertext cannot be re-extracted, so a sealed
                   OBJECT_KEY_ID:uint; LEAF_DIGEST:[ubyte];            // row's epoch and key live here only; LEAF_DIGEST:
                   COLUMNS:[ubyte]; }                                  // ciphertext sha2-256; COLUMNS: its extracted values
table FMBIdentity { ROW:uint; HASH:[ubyte]; }                          // IQC ingest identity (32 B)
table FMBLarge   { ROW:uint; ROOT_CID:[ubyte]; ROOT_NODE:[ubyte]; LEAF_DIGESTS:[ubyte]; }  // §4.2

table FMB {
  SELF_OFFSET:ulong;
  PREVIOUS:ulong;            // F of the previous non-record frame
  FEED_ID:uint;
  COMMITTED_AT:long;         // the round's clock (restamps instances on removals)
  TYPE_SEQ_HIGH:ulong;       // the type's highest seq issued so far (seqs never go back)
  ROWS:[FMBRow];             // in plan order; at most 65,536 per frame (a round splits beyond)
  DIGESTS:[ubyte];           // 32 B per NEW_FRAME row, in row order: the record CID's digest
                             // (a shared-frame row takes the digest of the frame it names)
  GROUPS:[FMBGroup];
  DICTIONARY:[FMBEntry];     // entries first used by this round (deltas)
  REMOVALS:[FMBRemove];
  URLS:[FMBUrl];
  SIGNATURES:[FMBSignature];
  SEALED:[FMBSealed];
  IDENTITIES:[FMBIdentity];
  LARGE:[FMBLarge];
}
root_type FMB;
file_identifier "$FMB";

What the vectors hold:

  • ROWS and GROUPS hold every column of a row.
  • DICTIONARY holds the node, batch, content-key, url and token strings that the round uses first. OBJECT_KEY entries are written only for sealed rows. Other rows' object keys come from their bytes, with ids given in order of first appearance in the stream, so a rebuild gives the same ids.
  • Why the digest stays. It is the commit's integrity check (§9) and the record's key. Without it, recovery could not tell a torn record frame from a good one, and a rebuild would have to re-hash every byte.
  • IDENTITIES holds the rows' ingest identities.
  • A move is MOVED_IN rows in the feed plus a MOVED_OUT removal in the local feed.

The instances, the token counts and the counters are folds over the rows.

Every change is an appended frame; nothing is changed in place:

  • DELETE, SUPERSEDE, CAT supersede, QUOTA and retention. An $FMB with REMOVALS and no rows.
  • A duplicate delivery's url. URLS.
  • A move. The feed's $FMB with MOVED_IN rows first, then the local feed's $FMB with MOVED_OUT. Recovery finishes a move that has only the first half.
  • A copy, retag or new instance. Rows that point at the existing frame.

#3.2$FCK: checkpoint (small; the state lives in segments)

FlatBuffers schema
enum fckSegmentKind : ubyte {          // the FSG kinds, §3.3
  DICTIONARY, LATEST, INSTANCES, TOKENS, TOMBSTONES,
  ROWS_BY_SEQ, ROWS_BY_OBJECT_EPOCH, ROWS_BY_CID, ROWS_BY_W, ROWS_BY_AT,   // the row orders, §7
  COLUMN = 64, ZONE_MAP = 65, ROLLUP = 66                                 // reserved: analytics, 64..127
}
struct FCKCounters {                   // the feed's counters
  ROWS:ulong; RECORDS:ulong; BYTES:ulong; RECORDS_NO_EPOCH:ulong;
  COPIES:ulong; COPY_BYTES:ulong; LIVE_FRAME_BYTES:ulong;
  MIN_SEQ:ulong; MAX_SEQ:ulong; MIN_EPOCH:long; MAX_EPOCH:long;
  MIN_TS:long; MAX_TS:long; MIN_AT:long; MAX_AT:long;
}
struct FCKSegment {                    // one live FSG frame. 48 bytes
  OFFSET:ulong; LENGTH:uint; KIND:fckSegmentKind; LEVEL:ubyte; RESERVED:ushort;
  MIN_SEQ:ulong; MAX_SEQ:ulong; COVERS_THROUGH:ulong; ENTRIES:ulong;
}
table FCK {
  SELF_OFFSET:ulong;
  PREVIOUS:ulong;
  FEED_ID:uint;
  TYPE:string; PROVIDER:string; SOURCE:string;   // the feed's identity: the type index is rebuilt from these
  GENERATION:uint;
  COMMITTED_AT:long;
  APPLIED_THROUGH:ulong;      // end (F+4+N) of the last FMB folded into the segments
  TYPE_SEQ_HIGH:ulong;
  COUNTERS:FCKCounters;
  SEGMENTS:[FCKSegment];
  SEGMENT_DIGESTS:[ubyte];    // 32 B per segment: its raw-leaf CID digest
  COMMITS_ROOT_CID:[ubyte];   // the commits tree (§4.3) as of APPLIED_THROUGH
  PREVIOUS_FEED_ROOT_CID:[ubyte];
}
root_type FCK;
file_identifier "$FCK";
  • Genesis. A new stream's first frame is an $FCK with zero counters and no segments. A stream names its own feed, and the type index is a cache.
  • Latest per object. Kept in the LATEST segments, not in the $FCK itself, so the checkpoint stays small. Each segment is sorted by object id, and the newest entry wins across segments.

#3.3$FSG: immutable state segment

FlatBuffers schema
struct FSGPair {             // the one sorted entry shape. 32 bytes
  KEY_HI:ulong; KEY_LO:ulong;
  RID:ulong;                 // SEQ << 16 | ROW_J

}
struct FSGLatest { OBJECT_KEY_ID:uint; RESERVED:uint; EPOCH:long; RID:ulong; ROW_REF:ulong; }  // 32 B
struct FSGInstance {         // one instance row. 88 B
  BATCH_ID:uint; CONTENT_KEY_ID:uint; RECORDS:ulong; BYTES:ulong; MIN_W:long; MAX_W:long;
  MIN_SEQ:ulong; MAX_SEQ:ulong; FIRST:long; UPDATED:long; MAX_AT:long; MAX_TS:long;

  SELF_OFFSET:ulong;
  PREVIOUS:ulong;
  FEED_ID:uint;
  KIND:fckSegmentKind;       // which vector is filled
  LEVEL:ubyte;
  MIN_SEQ:ulong; MAX_SEQ:ulong;
  COVERS_THROUGH:ulong;
  REPLACES:[ulong];          // F of the segments an LSM merge replaced
  ENTRIES:[FMBEntry];        // DICTIONARY, sorted by (KIND, ID)
  LATEST:[FSGLatest];        // LATEST, sorted by OBJECT_KEY_ID
  INSTANCES:[FSGInstance];   // INSTANCES, sorted by (BATCH_ID, CONTENT_KEY_ID)
  TOKENS:[FMBEntry];         // TOKENS: per-producer counts as TEXT [token, n, bytes, mints, maxts, maxseq]

  COLUMN:[ubyte];            // reserved (analytics)
}

#4IPFS mapping

#4.1Per-record blocks

  • For a record of N <= 1 MiB, the IPFS block is its range, with CID CIDv1(raw, sha2-256). This equals the record CID (unsealed) or the leaf CID (sealed).
  • The node registers (path of the generation file, F+4, N, CID) in Kubo's filestore (nocopy). The bytes stay where they are.
  • FlatSQL exposes these tuples through a read op. It answers RB1 rows (gen path, offset, length, cid, kind, unit) for a feed and a commit range, and the node pulls them per acknowledged round (§5).
  • Non-record frames ($FMB, $FCK, $FSG) are raw leaves the same way. The DAG links them in situ too.

#4.2Records over 1 MiB

  • Leaves. Leaf i is the range [F+4 + i*2^20, F+4 + min(N, (i+1)*2^20)), as a raw block.
  • Root. A dag-pb UnixFS File node:
    • links unnamed, Tsize = leaf size, in order;
    • Data = UnixFS{Type File, filesize N, blocksizes};
    • balanced and one level deep (the write pool caps a frame below 8 MiB, so a record has at most 8 leaves; a level is added only past 174 leaves).
  • The root CID equals what ipfs add --cid-version=1 --raw-leaves --chunker=size-1048576 gives for the same bytes. That is the interoperability check.
  • FMBLarge keeps the root CID, the root node's bytes (about 410 B for 8 leaves) and the leaf digests. The DAG and the CAR need no re-hash, and the node puts ROOT_NODE in its blockstore.
  • The whole-range raw CID (SDN's key) is never registered or provided: bitswap cannot move a block that large. The ROW entry maps the two CIDs to each other.

#4.3The feed root DAG

All link nodes are dag-pb, CIDv1, sha2-256. FlatSQL computes them as a pure function of the frames: they are never FlatSQL disk state. The node keeps them in its blockstore when exposure is on, and the CAR export emits them.

feed root                       dag-pb UnixFS Directory, links sorted by name
├── "checkpoint" -> the newest $FCK frame              raw leaf, in situ
├── "commits"    -> commits tree                       dag-pb, no Data; fanout <= 1,024
│     └── ... -> commit unit (one per FMB, stream order)  dag-pb, no Data, links in stream order:
│                  NEW record frames (raw leaf | §4.2 root), then the $FMB frame (raw leaf)
├── "segments"   -> node linking each live $FSG frame (raw leaf, in situ), in FCK.SEGMENTS order
└── "columns"    -> reserved for analytics column segments (absent)
  • Liveness.
    • A commit unit is linked while at least one row it added is live, or while it removes a row of a linked unit.
    • Its record links are only the live new frames.
    • A recursive pin of the feed root is the feed's live state, and nothing dead.
  • When the root changes.
    • The root is recomputed at each checkpoint (§6): the new units, the commits tree's right spine (O(depth) nodes), the segments node and the root.
    • Retention or a delete rewrites the touched units and their spine.
    • Compaction rewrites the whole tree.
  • What PREVIOUS_FEED_ROOT_CID gives. Inside the $FCK it is just bytes: a raw leaf has no links. History is reachable on purpose but never pinned by the current root.
  • Announcing. Only feed roots (and, if the node chooses, segment roots) are announced. Records are fetched by CID over bitswap from root holders.

#5Acknowledgment and durability

Rule. For one call, the writer:

  1. appends its record frames and then its feed's $FMB to each touched stream;
  2. syncs each touched stream once (in parallel when several);
  3. commits the SQLite index without a device sync (WAL, synchronous=NORMAL), for read-after-write;
  4. publishes and acknowledges.

What an acknowledgment promises. The record bytes and every column of their rows are durable in the stream. The index may be behind after a power loss, and recovery (§9) restores it from the $FMB frames.

Sync cost. A call pays one sync per touched stream. Syncing the index as well would make it two, so a single-feed call drops from 2 syncs to 1. A call that also creates a feed pays once for the feed: the new file, its genesis $FCK and a directory sync. A new token adds no sync, because it lives in the $FMB dictionary.

Order of persistence. The index commit is written only after its stream sync returned. A persisted index commit therefore never names bytes the stream lost. The index's mark is the end of the last $FMB it applied.

Background work keeps its own syncs off the acknowledgment path:

  • WAL checkpoints (they sync);
  • $FCK and $FSG frames (synced with the next round, or alone when idle);
  • merges of staged rows.

Registration follows the acknowledgment:

  • The node pulls (range, CID) tuples only for acknowledged rounds, so a filestore entry never names unacknowledged bytes.
  • The node syncs nothing extra. A crash that loses registrations is repaired by re-pulling from the node's last registered commit.

#6Checkpoints and segments

Cadence. A checkpoint is written when the first of these holds:

  • max(64 MiB, 4 x live segment bytes) of frames have been appended since the last one;
  • 65,536 rows have been appended since the last one;
  • the feed has had commits but has been idle for 30 s;
  • at close, at the end of a compaction, or before an export.

Writing one.

  1. Fold the rows since APPLIED_THROUGH into new level-0 segments, one per changed kind: dictionary entries, latest-per-object, instances, tokens, tombstones, and the row orders where enabled (§7).
  2. Append the segments, then the $FCK that lists every live segment.

LSM.

  • When a kind has 4 segments at a level, they merge into one at the next level (newest wins; tombstones drop the rows they name).
  • REPLACES names the inputs, which become dead frames.
  • Row-order segments merge only with neighbors in seq order, and a merge's output stays at most 1/8 of the feed's live rows. Retention by arrival therefore drops whole segments.

Open. Open reads the newest $FCK, its segments and the tail $FMBs after APPLIED_THROUGH. No SQLite file is needed for the counters, dictionary, instances, tokens or latest-per-object.

#7Index choice

  • The SQLite index (<feed>.db) is the default. It is a cache rebuilt from the $FMB chain (§9).
  • FSG row-order segments replace it for a workload only when every replay workload on the 15 GB fixture runs within about 10% of SQLite, native and AOT.
  • Reads go through the same reader and virtual-table interface over "segments + tail", where the tail is the in-memory view of the rows after the newest checkpoint.

#8Backups and archives: CARv2

A backup of a feed is the CARv2 of its feed root. A store or type backup is the CAR of a dag-pb UnixFS Directory <TYPE>/<feed>, whose links are the feed roots.

Bytes.

  • Pragma 0a a1 67 76 65 72 73 69 6f 6e 02 (11 B).
  • CARv2 header (40 B): characteristics 0, data offset 51, data size, index offset.
  • CARv1 payload:
    • the dag-cbor header {roots: [root], version: 1};
    • sections varint(len(cid)+len(data)) | cid | data in deterministic DFS pre-order from the root, each block once at its first occurrence;
    • in order: the root, "checkpoint", "commits" (interior node, unit node, its leaves in stream order; a large record's root, then its leaves), "segments" and its leaves.
  • MultihashIndexSorted index (0x0401), as go-car writes it.

The same state always gives the same CAR bytes. There is no custom container.

Restore.

  • ipfs dag import works as is.
  • FlatSQL restore walks the CAR in order. For each unit it appends the new record leaves as frames, then applies the unit's $FMB through the writer in replay mode. Seqs, timestamps, delivery times, nodes, batches, urls, signatures and identities are kept. Only OFFSET is local, so it is remapped and written into a fresh $FMB.
  • This is the same apply code as crash recovery and rebuild (§9): one path.
  • Pass condition: every replay answer hashes equal to the source's.

Backups are tables themselves.

  • A restored backup is a feed and serves as a table.
  • A backup set is a feed-root DAG of the same shape, so it can be pinned, announced, backed up and restored like any feed: recursive storage.
  • The backup catalog is a feed of $DPM records, one record per CAR. The node writes them, because a DPM is signed by its provider. The catalog feed is itself backed up the same way.
    • DATASET_ID is <TYPE>/<provider>@<source>. UPDATE_ID is the feed root CID's text. PROVIDER_PEER_ID, PUBLISH_TIMESTAMP and PROVIDER_SIGNATURE come from the node.
    • Each CAR is one ASSETS entry, TRANSPORT_KIND = CONTENT_ADDRESS: CID and DATA_ROOT are the feed root, BYTE_LENGTH is the CAR's size and FILE_NAME is the CAR's name.
    • Two additive DPM fields, in the same SDS release as FMB, FCK and FSG (1.255.0), carry the rest:
      • publicationAssetKind.CAR_ARCHIVE;
      • DPMAsset.THROUGH_SEQ:ulong, the highest seq the archive covers (its as-of point).

#9Crash recovery from the stream tail

The commit point. A commit point is a verified non-record frame on the commit chain. An $FMB verifies when all of these hold:

  • the FlatBuffers Verifier passes on its aligned copy;
  • SELF_OFFSET = its F;
  • PREVIOUS = the last commit point's F;
  • every NEW_FRAME row names a whole frame between the previous commit point and it;
  • each such frame's sha2-256 equals the row's digest (or LEAF_DIGEST, sealed).

An $FCK or $FSG verifies on the first three. The digest check makes recovery safe even when a crash persisted later pages before earlier ones.

Open, per feed:

  1. Start.
    • With an index: start at its mark. A stream shorter than its mark lost acknowledged frames, and the feed is quarantined (P4_E_CORRUPT, named).
    • Without one: find the newest $FCK by the tail search below and load its segments.
  2. Walk forward from the start, collecting record frames until a candidate commit point. If the candidate verifies, apply it with its seqs and metadata. Rows get no fresh seqs, and provenance is never blank.
  3. Cut the tail. At EOF, or at a torn or unverifiable frame, cut the stream back to the end of the last commit point. Those bytes were never acknowledged and never registered.
  4. Finish moves. A MOVED_IN row in a feed whose MOVED_OUT is missing in the local feed gets its removal $FMB appended to the local feed.
  5. Rebuild caches as needed:
    • the views from the index's staged rows;
    • a missing or damaged .db from the $FMB chain;
    • a missing .idx from the genesis frames.

Tail search (no index).

  • Read the stream backward in 1 MiB chunks.
  • A candidate is a position p with "$FCK" at p, giving F = p - 8.
  • Accept it only if all of these hold: it verifies, SELF_OFFSET = F, its PREVIOUS names a frame that ends exactly at F and verifies as a commit point, and the forward walk from it reaches EOF or a torn tail.
  • The checkpoint cadence bounds the search to about 64 MiB. On any doubt, the search falls back to a forward walk of the size prefixes, which is a sequential read of the file.

Rebuilding the SQLite index without its file.

  • Walk the stream forward in one sequential read. Apply each $FMB in one bulk transaction, with the secondary indexes built after.
  • The epoch and object key of each unsealed row are re-extracted from its record frame, which is already in the read buffer (principle 6).
  • Nothing is re-hashed except the tail after the newest checkpoint.
  • Open without the SQLite index needs none of this: the newest $FCK and its segments already hold the epoch and object orders.

#10Retention and compaction (pins and filestore first)

Retention, QUOTA_GC, DELETE, SUPERSEDE:

  1. Append the removal $FMB and sync. The decision is now durable.
  2. Remove the index rows. Reads stop answering them.
  3. Publish the drop list (CID, unit) and the next feed root at the next checkpoint (or at once when the feed is exposed).
  4. The node does pin update old-root -> new-root, removes the dropped CIDs' filestore entries (reference-counted across feeds, §11) and calls p4 release(feed, through-commit).
  5. Only released bytes may physically go (step 2 of a compaction). A feed that is not exposed is released implicitly.

The stream is append-only, so no byte under a live filestore entry is ever changed. Retention by arrival drops whole FSG segments (§6).

Compaction (a stream more than half dead, with at least 1 MiB dead):

  1. Write generation g+1: genesis $FCK, the live record frames in stream order, consolidated $FMBs (rows COMPACTED, new offsets, at most 65,536 per frame), fresh segments, and the final $FCK. Then sync.
  2. Repoint the index (one transaction) and publish the moved ranges and the new root.
  3. The node re-registers the same CIDs at their new (path, offset) and pin-updates to the new root. Record CIDs do not change, because records are verbatim. Then it releases generation g.
  4. Unlink g after the release and after the 30 s reader window.

A node that never releases blocks compaction, and the store reports it as a stat. It never loses data.

#11The node's side

The node, not FlatSQL, runs the IPFS side of a feed:

  • Filestore. Kubo filestore (nocopy) in the in-process Kubo, with the store directory inside the filestore root. Registration goes through filestore.FileManager.Put with PosInfo{FullPath, Offset}. ipfs add is not used: it re-chunks.
  • Registration per batch. The node pulls the acknowledged rounds' tuples, puts them in the filestore in one datastore batch, and keeps a per-feed "registered through" commit.
  • Reference counts. Filestore entries are keyed by multihash. A record held by two feeds has one entry: the node counts holders, and on a drop re-points the entry to a remaining holder, never deleting it.
  • Roots only. The node announces feed roots (and optionally segment roots). It never provides record CIDs.
  • Per-feed policy, off by default. Restricted feeds (UDL, and anything not on ipfs_schemas) are never registered, provided or served. Encrypted feeds are addressed by ciphertext.
  • Unpin on retention and compaction, per §10, then release.
  • Backup catalog. The node writes one signed $DPM per CAR into the catalog feed (§8).
